# План фотопроверки к защите

## Маршрут учителя

1. **Последние контрольные.** Главная показывает работы от новых к старым. Учитель может отфильтровать их по классу, открыть существующую или нажать «Создать контрольную».
2. **Создание.** В окне учитель явно выбирает математику или физику, прикладывает фото условия, вводит заметки о том, как проверять, и выбирает класс. В заметках можно задать общий подход, требования к способу решения и максимальные баллы за конкретные номера. Пример — «№ 1 — 3 балла. № 2 — 2 балла. В № 2 обязательно указать единицы». Перед сохранением показываем извлечённые максимумы по номерам.
3. **Сбор решений.** После сохранения сервер начинает читать условия и готовить солверы. Учитель сразу попадает в сбор работ и загружает ZIP с фотографиями или выбирает несколько снимков. Кабинет находит или создаёт ученика по ФИО в имени файла и объединяет страницы одного ученика в одну сдачу. Интерфейс показывает, какие работы связаны с учениками и где нужно уточнение.
4. **Ведомость.** Строка — ученик, столбцы — задания. В ячейке видны балл из максимума и краткое замечание по рассуждению. В конце строки — набранные баллы, итоговая оценка и статус. Оценка изначально пустая. Работы, которые совсем не распознаны, и работы со спорными фрагментами выделены разными статусами. Учитель видит, где требуется его решение.
5. **Проверка ученика.** Клик по имени открывает окно с упорядоченными сканами, подсветкой, объяснением ошибок и рекомендациями. Кнопки «2», «3», «4», «5» сохраняют оценку сразу. «Предыдущий» и «Следующий» переключают ученика в порядке текущей ведомости без закрытия окна. Здесь же учитель может исправить балл, отредактировать отзыв и опубликовать результат.
6. **Итоги.** На отдельной странице учитель видит по каждому заданию долю неверных ответов, повторяющиеся ошибки и темы для разбора с классом. В индивидуальном отзыве — ошибки, темы для повторения и оценка в конце, если её выставили. Опубликованный отзыв можно скачать в Markdown.

## Согласования до старта

№ 1 ведёт публичный API и события, № 2 определяет внутреннюю обработку, № 3 проверяет, что данных хватает для экранов. Предлагаемые решения ниже и в [JSON-примерах](photo-demo-contract.json) — общий черновик стыков. После сверки каждый работает в своей ветке и использует те же примеры для моков или тестов.

Создание** | Действующий `POST /v1/classes/{classId}/assignments` принимает фото условия в `file`, явный `subject`, `title`, `requirements` и необязательный `taskPoints` со списком `{taskNumber, maxScore}`. Сохраняем заголовок и дату, чтобы главная могла показать сохранённую работу после обновления страницы. После получения `assignmentId` и `assignmentRev` открывается сбор работ. |

В JSON блоки с суффиксом `Multipart` перечисляют поля и имена файлов для запроса. `requirements` и `taskPoints` передаются JSON-строками в форме. Блоки `assignmentPublishedEvent` и `attemptSubmittedEvent` предназначены для тестов воркера. Для чтения после публикации применяем `checkReadyAfterPublishOverrides` поверх `checkReady`. Для сценария со спорным фрагментом применяем `checkNeedsReviewOverrides` поверх `checkReady`.

### Правила демо

**Фото условия и требования.** JPEG, PNG или WebP. Для первой версии одна фотография условия с читаемыми номерами. Учитель подтверждает новые требования при сохранении. Фронтенд извлекает в `taskPoints` явно указанные максимумы, показывает их и сохраняет сам текст требований. Несовместимые максимумы у одного номера требуют исправления до сохранения. Распознавание условий не заменяет постановку задачи и не додумывает числа или рисунки. Если номера или определяющая часть условия не читаются, отображаем проблему и даём заменить фото или уточнить распознанный текст. Для физики проверяем, что единицы дошли до солвера и проверки.

**Группировка страниц.** Фото одной страницы называется `Смирнова Анна.jpg`, страницы одной работы — `Смирнова Анна__01.jpg`, `Смирнова Анна__02.jpg`. Префикс до номера ищем среди активных учеников выбранного класса по нормализованному полному имени. При одном совпадении привязываем, при нуле создаём ученика с валидным именем. Тёзки, неполное имя и `IMG_0452.jpg` требуют ручной привязки. Для многостраничной работы номер в имени определяет порядок, индексы в API начинаются с нуля. Дубли номера или пропуски в нумерации требуют уточнения до отправки группы на проверку. Ручная привязка применяется ко всей группе. Если нужно добавить страницу после импорта, учитель повторно отправляет полный комплект. Тот же упорядоченный комплект байтов сохраняет попытку и проверку для той же ревизии задания, изменённый комплект создаёт новую попытку. Лимиты размера и проверку содержимого ZIP применяем до создания групп. Действующие маршруты загрузки DOCX и ZIP с DOCX нужны для прежних сценариев. [Памятка об именах файлов](photo-filenames.md)

**OCR и спорные места.** Воркер распознаёт по очереди страницы одной сдачи, сохраняет снимки отдельно и объединяет расшифровки в одно решение со ссылкой на страницу и строку. Продолжение задания на следующем развороте относится к тому же номеру. `photoMarks` связываются с замечаниями по `(taskId, issueId)` и указывают `pageIndex`, `lineIndex` с нуля внутри расшифровки этой страницы и `box` в относительных координатах ориентированного фото. Если известна строка, но область ненадёжна, показываем строку без рамки. `ocrStatus` принимает `readable`, `needs_review` или `unreadable`. Для полностью неразборчивой работы показываем «Не распознана» с причиной и, если номера условий уже известны, даём черновик для ручной оценки по оригиналу. Для частично нечитаемой или неоднозначной показываем «Требует перепроверки» с конкретным заданием или фрагментом. Сбой провайдера отображаем через состояние проверки и его причину.

**Баллы и оценка.** `taskAssessments` содержит `taskId`, `score`, `maxScore` и `comment`. Максимум берём из требований, по умолчанию — 1. Для демо однозначно выполненное задание получает максимум, однозначно неверное или пропущенное — 0, а спорное — `null` до решения учителя. Учитель может поставить частичный балл в пределах максимума. `total` содержит набранную сумму, максимальную сумму и число заданий без балла, которые в ведомости нужно пометить. Школьная `grade` — отдельное целое 2–5 или пустое значение, которое задаёт учитель. Она сохраняется сразу как черновик, а в опубликованном отзыве появляется после публикации выбранной ревизии.

**Правки и публикация.** Через версионный `PATCH /review` передаём `set_grade`, `set_teacher_comment` и `set_task_score` с `taskId`. Внутренние имена — `setGrade`, `setTeacherComment`, `setTaskScore`. `null` очищает значение. Если очищен балл задания, ячейка снова ждёт решения учителя. Отдельное изменение вердикта проходит через существующую операцию. При повторной отправке используем тот же `editId`, при конфликте `409` перечитываем результат и сохраняем ввод. Каждый опубликованный Markdown остаётся привязан к своей ревизии. Структура отзыва — ошибки и исправления по заданиям, рекомендации по темам, затем оценка, если выставлена.

**Сводка класса.** В расчёт берём одного ученика один раз по выбранной ревизии варианта. При наличии публикации берём последнюю опубликованную ревизию, до первой публикации — последний готовый черновик. Отдельно показываем несдавших, ожидающих и неразборчивые задания. Доля неверных ответов по заданию и доля затронутых каждой категорией считаются от числа уникальных сдавших. Пример — «Задание № 2 неверно решили 7 из 10 сдавших (70%)». Две одинаковые ошибки одного ученика дают одного затронутого ученика. Связываем повторяющиеся категории с темами для разбора и примерами замечаний. Неразборчивость и ожидание не превращаются в неверный ответ.

## Слияние и приёмка

1. **Общий старт.** Согласовать HTTP и события из JSON. № 1 ведёт общую ветку контрактов, № 2 подтверждает форматы источников и результата, № 3 проверяет переходы экранов. Сразу начать формы, парсер ZIP и извлечение условий параллельно.
2. **Первый совместный прогон.** Сначала обновить читатель нового события в `grading`. Затем включить передачу фото условия и `pageRefs` из кабинета. Прогнать одно фото условия, ZIP с двумя страницами одного ученика и одной страницей другого, эталон и один готовый результат. Сверить число учеников, сдач и проверок.
3. **Подключение фронтенда.** На совместном стенде сверить снимки, баллы и состояния ведомости. Проверить переход между учениками, оценку, перечитывание, публикацию и выгрузку отзыва. Затем открыть тренды и сравнить числа с манифестом. Для первого прогона подойдут сохранённые ответы OCR, для приёмки нужна репетиция на фото.
4. **Готовность к защите.** Запустить `uv run pytest` и `uv run mypy`, из `frontend` — `npm run build` и `npm run lint`. Повторить полный сценарий с чистого класса, повторно загрузить тот же ZIP и убедиться, что сводка осталась прежней. [Запуск E2E](../../CONTRIBUTING.md#сквозной-сценарий-e2e)
